# مكتبة تحديات النصوص والقوائم

مشروع تدريبي مستقل بعد وحدة الخوارزميات. كل الكلمات والأرقام خيالية، ولا يقرأ البرنامج بيانات شخصية أو يكتب ملفات. اختر لغة أولًا ثم قارن النسخة الأخرى. لا تحتاج OOP.

## التشغيل على Windows

المطلوب Python 3.10+ أو Node 22+ مع المكتبات القياسية فقط. افتح PowerShell في مجلد الحزمة. لا توجد اعتمادات ولا تحتاج npm أو pip.

```powershell
Set-Location python
python --version
'{"task":"count","text":"red blue red"}' | python main.py
python -m unittest -v
Set-Location ..
Set-Location javascript
node --version
'{"task":"window","items":[-5,-2,-4],"k":2}' | node main.cjs
node test.cjs
```

إذا لم يكن python معروفًا، شغّل أوامر Python نفسها باستخدام `py -3` إن كان Python Launcher مثبتًا. لا حاجة إلى تغيير ExecutionPolicy.

## الملفات والمسؤوليات

- `python/rules.py` و`javascript/rules.cjs`: دالة `solve(data)` تعيد النتيجة وحدها، مع دوال الحساب والتحقق. لا تقرأ ولا تطبع ولا تغيّر المدخل.
- `main.py` و`main.cjs`: قراءة كائن JSON واحد من stdin وطباعة `{ "result": ... }` أو `{ "error": "invalid input" }` في سطر واحد. الإدخال الفارغ أو JSON المكسور خطأ أيضًا. NaN وInfinity و-Infinity ليست JSON صالحًا وتُرفض حتى في حقل زائد؛ parse_constant في Python يستدعي reject_constant عند هذه الكلمات لمساواة رفض JSON.parse في Node. البرنامج لا ينتظر أكثر من كائن؛ أنهِ الإدخال عبر pipe أو نهاية stdin.
- `fixtures.json`: حالات سلوكية بمدخل ونتيجة صريحين، مشتركة بين اللغتين.
- اختبارات اللغة: تقارن الاستدعاء المباشر وCLI بالـfixtures وتفحص عدم تغيير المدخل؛ وتختبر JSON مكسورًا. المسافات في طباعة JSON لا تغيّر المعنى.

في Python يجلب `import json` محلّل JSON القياسي، و`sys.stdin.read()` يقرأ الإدخال كله، و`json.loads` يفك النص، و`json.dumps` يكتبه. `if __name__ == "__main__"` يمنع تشغيل CLI عند الاستيراد للاختبار. في Node ملفات `.cjs` تعني CommonJS؛ `require("node:fs")` مكتبة قياسية و`readFileSync(0,"utf8")` يقرأ stdin من الوصف 0. `require("./rules.cjs")` يجلب الوحدة المحلية و`module.exports` يعلن أسماءها. `require.main === module` حاجز نقطة الدخول. تستعمل الاختبارات `node:assert/strict` للمقارنة و`node:child_process` لتشغيل CLI محليًا؛ لا توجد شبكة أو حزمة خارجية.

## العقد

نقبل كائنًا وفيه `task` واحد من `count` و`pair` و`window` و`report`. الحقول الزائدة تُتجاهل. الأنواع والحدود تُفحص صراحة؛ لا نحوّل نصًا إلى عدد ولا نعدّ bool عددًا.

| المهمة | الحقول المطلوبة | النتيجة داخل result |
| --- | --- | --- |
| count | text | أزواج [كلمة، عددها] بترتيب أول ظهور |
| pair | items مرتبة وtarget | فهرسا أول تطابق من الطرفين، أو [] |
| window | items وk | أكبر مجموع لمقطع متجاور طوله k |
| report | text وitems وk | {counts: الأزواج، maxWindow: أفضل مجموع} |

`text` من صفر إلى 200 حرف، من الأحرف الإنجليزية الصغيرة `a` إلى `z` ومسافة ASCII فقط. افصل على المسافات وتجاهل الأجزاء الفارغة؛ النص الفارغ أو المسافات وحدها يعطي []. لا ندّعي معالجة العربية أو تقسيم Unicode في هذا التحدي. الحروف الكبيرة وtab وnewline داخل النص مرفوضة.

`items` قائمة من صفر إلى 30 عددًا صحيحًا بين -20 و20، و`target` عدد صحيح بين -40 و40. قد تتكرر القيم وقد تكون صفرًا أو سالبة. لا تقبل bool أو كسورًا أو نصوصًا بدل أعداد. `pair` فقط يتطلب ترتيبًا تصاعديًا؛ يبدأ left=0 وright=n-1 ويعيد أول مساواة في مساره مع left<right. لذلك [0,0,0] وهدف0 تعيد [0,2]، والعنصر الوحيد لا يُستعمل مرتين. الفهارس تبدأ من صفر. لا تفرز القائمة لتخفي خطأ المدخل.

`k` عدد صحيح من صفر إلى طول items. عند k=0 النتيجة 0، وعند k>0 هيّئ أفضل مجموع من نافذة حقيقية حتى إذا كانت كل الأعداد سالبة. `report` لا يحتاج target ولا ترتيب القائمة لأنه يجمع العدّ والنافذة فقط. المدخل المخالف يعطي الخطأ المعلن. نعني بالعدد الصحيح قيمة بلا جزء كسري: `2.0` في JSON تقابل 2 في Node، ولذلك نقبلها أيضًا في Python. تفحص integer_in النوع والقيمة وتستبعد bool؛ ثم تحول k إلى int كي يصلح فهرسًا في Python. أما `2.5` و`true` فمرفوضان. مقارنة الاختبار تعتمد معنى JSON، لذلك 2 و2.0 متساويان عدديًا في النتائج.

## خطوات الإنجاز والأدلة

هذه نسخة البداية. يوجد TODO واحد في solve لكل لغة، ورفع NotImplementedError("complete solve") أو Error("complete solve") مقصود. لذلك يفشل الاختبار الواحد في كل لغة عند أول fixture قبل التنفيذ، ولا تمثل هذه النتيجة عيبًا في بيئتك. استبدل موضع TODO بدالة توجيه وحساب وتحقق وأضف دوالًا كما تشاء. بعد الإنجاز يجب أن يمر الاختبار بجميع الحالات. لا تنسخ إجابات fixtures إلى الحل.

1. ابدأ بالعدّ وراجع ترتيب أول ظهور، ثم pair مع سبب حركة كل مؤشر.
2. نفّذ window وراجع الفراغ وk=0 وk=n والسالب والأفضل في آخر نافذة.
3. ركّب report من الدوال نفسها وضع التحقق عند حد المكتبة.
4. شغّل الاختبارات من مجلد اللغة. الاختبار الواحد يمر بجميع الـfixtures ثم JSON المكسور؛ فشله عند أول حالة لا يعني أن بقية الحالات نجحت أو نُفذت.
5. اشرح مثالًا مضادًا لكل تخمين خاطئ. قارن حل النافذة بحل مباشر على حالات صغيرة، وعدّ قراءات العناصر بدل قياس الزمن. مراجعة الشرح البشرية منفصلة عن نجاح الاختبارات.

الدوال الحسابية تفترض أن solve تحققت من العقد. خريطة العدّ تستخدم مساحة بحسب الكلمات المختلفة؛ pair وwindow تستخدمان مساحة إضافية ثابتة. تهيئة النافذة تجمع أول k عناصر بحلقة فهارس دون نسخ مقطع، ثم تقرأ عنصرين لكل تحديث. إرجاع قائمة الأزواج يحتاج مساحة للمخرج في اللغتين.
